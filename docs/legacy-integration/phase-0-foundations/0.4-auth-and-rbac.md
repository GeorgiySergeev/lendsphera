# Phase 0 · Step 4 — Auth and RBAC

## Context

Auth is partially in place: the DB has `User`, `Session` (79 rows),
`OAuthAccount`, `ApiKey` models. What is missing:

- JWT strategy in `apps/api` so NestJS can validate tokens issued by Auth.js.
- Role-based guards using the existing `Role` enum.
- `apps/web` Auth.js config pointing at the real API login endpoint.

## Goal

End-to-end auth: sign in via `apps/web` → Auth.js issues a JWT that `apps/api`
validates → Nest guards enforce roles per route.

### `apps/api/src/auth/auth.controller.ts`

- `POST /v1/auth/login` → `{ accessToken, refreshToken, user }`
- `POST /v1/auth/refresh` → `{ accessToken }`
- `GET /v1/me` → current user (requires `JwtAuthGuard`)

### `apps/api/src/auth/jwt.strategy.ts`

`PassportStrategy(Strategy)` with `secretOrKey` from `ConfigService`.

`validate(payload)` returns `{ userId, email, role }`.

Token payload must include `role` so `RolesGuard` works without a DB query on
every request.

### `apps/api/src/auth/roles.guard.ts`

```typescript
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(ctx: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<Role[]>("roles", [
      ctx.getHandler(),
      ctx.getClass()
    ]);
    if (!required?.length) return true;
    const { user } = ctx.switchToHttp().getRequest();
    return required.includes(user?.role);
  }
}
```

### `apps/api/src/app.module.ts`

Register guards globally:

### `apps/web/src/app/api/auth/[...nextauth]/route.ts`

Only create if Auth.js is NOT already configured (check Inputs step 3).

```typescript
import NextAuth from "next-auth";
import Credentials from "next-auth/providers/credentials";

export const { handlers, auth, signIn, signOut } = NextAuth({
  providers: [
    Credentials({
      async authorize(credentials) {
        const res = await fetch(
          `${process.env.API_INTERNAL_URL}/v1/auth/login`,
          {
            method: "POST",
            headers: { "Content-Type": "application/json" },
            body: JSON.stringify(credentials)
          }
        );
        if (!res.ok) return null;
        const data = await res.json();
        return { ...data.user, accessToken: data.accessToken };
      }
    })
  ],
  callbacks: {
    jwt({ token, user }) {
      if (user) {
        token.accessToken = (user as any).accessToken;
        token.role = (user as any).role;
      }
      return token;
    },
    session({ session, token }) {
      session.accessToken = token.accessToken as string;
      session.user.role = token.role as string;
      return session;
    }
  }
});

export const { GET, POST } = handlers;
```

## Acceptance criteria

- `POST /v1/auth/login` with a seeded user returns
  `{ accessToken, refreshToken, user: { id, email, role } }`.
- `GET /v1/me` returns 401 without token, 200 with valid token.
- An endpoint decorated `@Roles(<admin-role-value>)` returns 403 for a user with
  a lower role.
- Auth.js session in `apps/web` exposes `session.accessToken`.
- Existing `Session` rows (79) and `OAuthAccount` rows are NOT touched.
- No new columns or migrations are introduced in this step.

## Out of scope

- Password reset / email verification.
- External OAuth providers (`OAuthAccount` exists but not wired here).
- Per-landing or per-workspace access control.
- Refresh token rotation (single refresh endpoint is sufficient for now).
